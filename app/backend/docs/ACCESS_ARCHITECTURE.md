# Архитектура прав доступа и масштабируемость

## Текущая схема

```
Keycloak (IdP)                    Backend (источник прав)
─────────────────                 ───────────────────────
• Аутентификация                 • Роли (roles)
• JWT (sub, name, login)         • Права на роли (role_permissions)
• Без привязки к ролям приложения • Назначение ролей пользователям (user_roles по external_id = sub)
                                 • GET /profile/me/permissions → byEntity для фронта
```

- **Identity** (кто ты) — Keycloak: `sub`, имя, логин.
- **Authorization** (что можно) — только бэкенд: роли и права в БД, привязка по `external_id` (Keycloak `sub`).

Так можно менять IdP или иметь несколько реалмов без переписывания логики прав.

## Масштабируемость

### Что уже ок

| Аспект | Реализация |
|--------|------------|
| Разделение IdP и прав | Keycloak не знает про роли приложения — масштабируется замена IdP, мультитенант по реалмам |
| Нормализованная модель | Роли → права (N:M), пользователи → роли (N:M), добавление новых прав без миграции схемы (новая строка в enum + role_permissions) |
| Один запрос за правами | `getPermissionsForUser` — 2 запроса (user_roles + role_permissions), результат можно кешировать по `external_id` |
| Гибкие роли | Роли и набор прав задаются в приложении, без деплоя Keycloak |

### Что улучшить при росте

1. **Кеш прав**  
   При большом RPS: кеш (Redis/Memory) по `external_id` с TTL 1–5 мин, инвалидация при изменении `user_roles` или `role_permissions` для этого пользователя/роли.

2. **Проверки на маршрутах**  
   Сейчас только `verifyToken` глобально. Для жёсткого контроля — повесить `requirePermission([...])` на конкретные эндпоинты (create/update/delete), чтобы даже при баге на фронте бэкенд возвращал 403.

3. **Индексы**  
   Уже есть `idx_user_roles_external_id`, `idx_user_roles_role_id`, `idx_role_permissions_role_id`. При росте таблиц — мониторинг планов запросов.

4. **Аудит**  
   При необходимости — таблица `audit_log` (кто, когда, какое действие, по какой сущности) и логирование смены ролей/прав.

5. **Мультитенант**  
   Если появятся «организации»/«реалмы»: добавить `tenant_id` в `roles` и в привязки, фильтрация по tenant в запросах прав.

Итого: база архитектуры масштабируемая; кеш, проверки на API и аудит добавляются по мере необходимости.

## Первый администратор

### Вариант 1: Через UI (без настройки)

1. Применить миграции (создаётся роль «Администратор» со всеми правами).
2. Войти в приложение под пользователем Keycloak.
3. Настройки → вкладка **«Управление доступом»**.  
   Пока в системе ни у кого нет права «Управление доступом», эта вкладка доступна любому авторизованному пользователю.
4. В блоке **«Пользователи и роли»** нажать **«Назначить роли»** у своего пользователя и выбрать роль **«Администратор»** → Сохранить.
5. Дальше только пользователи с этой ролью смогут заходить в «Управление доступом».

### Вариант 2: Через переменную окружения (автоназначение при старте)

В `.env` или в переменных окружения сервера задать:

```bash
FIRST_ADMIN_EXTERNAL_ID=<keycloak_sub_пользователя>
```

где `keycloak_sub` — это `sub` из JWT Keycloak (UUID). Узнать его можно:

- в Keycloak Admin → Users → пользователь → ID (или атрибуты);
- или после первого входа — из ответа `GET /api/v1/profile/me` (поле `keycloak.sub`).

При старте бэкенда скрипт `ensureFirstAdmin` (см. `src/scripts/ensureFirstAdmin.ts`) назначит этому пользователю роль «Администратор», если её ещё нет. Переменную можно не задавать или убрать после первого деплоя.

### Вариант 3: Вручную в БД

После первого входа пользователя (чтобы в `user_profiles` появилась запись с `external_id`):

```sql
INSERT INTO user_roles (external_id, role_id)
SELECT '<sub из Keycloak>', id FROM roles WHERE code = 'administrator'
ON CONFLICT (external_id, role_id) DO NOTHING;
```

## Файлы

- `src/enums/permissions.ts` — коды прав и группы для UI.
- `src/services/permission.service.ts` — получение прав по `external_id`.
- `src/middlewares/accessManagement.middleware.ts` — допуск в раздел управления доступом (bootstrap: если ни у кого нет права — доступ открыт).
- Миграции: `036_*` (таблицы прав), `037_*` (display_name в профиле), `038_*` (роль Администратор).
