# Анализ проблемы: потеря данных БД при деплое

## Симптомы

- После каждого деплоя инциденты и все данные приложения пропадают.
- В логах бэкенда видно: применяются миграции с 001 по 038, затем Sequelize создаёт таблицы (`CREATE TABLE IF NOT EXISTS`), запускаются сидеры — то есть БД воспринимается как **пустая**.

## Что это значит

Бэкенд при старте подключается к Postgres и видит пустую БД (нет таблицы `migrations` или нет записей в ней). Значит выполняется одно из двух:

1. **Postgres отдаёт пустую БД** — контейнер использует том без данных или с «новой» инициализацией.
2. **Бэкенд подключается не к тому Postgres** — другой хост/порт/БД (например, другой контейнер или внешний сервер).

Ниже разобраны возможные причины и как их проверить.

---

## Возможные причины (по приоритету)

### 1. `docker compose down` + пересоздание контейнера Postgres

**Суть:** При деплое в workflow вызывается `docker compose down`. Все контейнеры удаляются, тома по умолчанию **остаются**. При следующем `docker compose up -d --build` контейнер Postgres создаётся заново и должен подключить тот же том (`ims_ims-db-data`). Данные должны сохраняться.

**Почему данные всё же могут пропадать:**

- В части окружений или версий Docker/Compose при пересоздании контейнера том мог подключаться некорректно или использоваться другой том (см. п. 2).
- Явное удаление томов: если где-то вызывается `docker compose down -v` или `docker volume rm`, данные будут теряться.

**Рекомендация:** Не вызывать `docker compose down` в деплое — только `docker compose up -d --build`. Тогда контейнер Postgres не пересоздаётся, том не отключается, данные не теряются. Для полного перезапуска стека на проде использовать `docker compose down` **без флага `-v`**.

---

### 2. Разные имена томов / project name

**Суть:** Имя тома в Docker Compose по умолчанию имеет вид `{project}_{volume}`. Имя проекта берётся из имени каталога (откуда запускается `docker compose`). Если деплой один раз идёт из `~/ims`, другой — из `~/ims-new` или другого каталога, получаются разные проекты и **разные тома** (например, `ims_ims-db-data` и `ims-new_ims-db-data`). Один том с данными, другой пустой — после деплоя может подняться контейнер с пустым томом.

**Что сделано:** В `docker-compose.yaml` для тома БД задано явное имя:

```yaml
ims-db-data:
  name: ims_ims-db-data
```

Так один и тот же том используется независимо от каталога и project name.

**Проверка на сервере:**

```bash
docker volume ls | grep ims
docker inspect ims-postgres --format '{{range .Mounts}}{{.Name}} {{end}}'
```

Ожидается том `ims_ims-db-data`, подключённый к контейнеру `ims-postgres`.

---

### 3. Backend подключается не к тому Postgres

**Суть:** В контейнер бэкенда переменные передаются из `.env` сервера: `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`. Если на сервере в `.env` указан другой хост (например, `localhost` или внешний сервер), бэкенд будет ходить в другую БД. Она может быть пустой или пересоздаваться отдельно.

**Ожидаемые значения на проде:**

- `BACKEND_POSTGRES_HOST=ims-postgres` (имя сервиса в одном compose с бэкендом)
- `BACKEND_POSTGRES_PORT=5432`
- `BACKEND_POSTGRES_DB=ims` (или как у вас)

**Проверка на сервере:**

```bash
cd ~/ims
grep BACKEND_POSTGRES .env
docker exec ims-backend env | grep POSTGRES
```

Убедиться, что внутри контейнера бэкенда `POSTGRES_HOST=ims-postgres` и порт/БД совпадают с тем Postgres, который использует том `ims_ims-db-data`.

---

### 4. Путь данных Postgres и монтирование тома

**Суть:** В compose для приложения используется монтирование тома в каталог **выше** данных:

```yaml
ims-postgres:
  volumes:
    - ims-db-data:/var/lib/postgresql
```

Официальный образ Postgres по умолчанию использует `PGDATA=/var/lib/postgresql/data`. То есть данные лежат в `volume/data/`. Это корректно: при первом запуске Postgres инициализирует кластер в `/var/lib/postgresql/data`, при следующих запусках с тем же томом видит уже существующие данные.

**Риск:** Если раньше том монтировался как `/var/lib/postgresql/data` (тогда данные были в корне тома), а потом конфиг сменили на `/var/lib/postgresql`, Postgres увидит пустой каталог `data` и переинициализирует кластер. Сейчас в репозитории везде используется `/var/lib/postgresql` — важно не менять это на проде без миграции данных.

**Проверка на сервере:**

```bash
docker inspect ims-postgres --format '{{json .Mounts}}' | jq
sudo ls -la /var/lib/docker/volumes/ims_ims-db-data/_data/
```

В томе должен быть каталог `data` с содержимым (например, `base`, `global`, `pg_wal`). Если в `_data` только пустой каталог `data` после нескольких деплоев — возможна переинициализация из-за смены пути или пустого тома.

---

### 5. Удаление тома вручную или скриптом

**Суть:** Тома удаляются только при:

- `docker compose down -v` или `docker compose down --volumes`;
- `docker volume rm ...`;
- очистке системы с удалением неиспользуемых томов (например, `docker system prune -a --volumes`).

**Рекомендация:** В деплое и на проде **никогда** не использовать `-v`/`--volumes` с `down` и не удалять том `ims_ims-db-data`. В workflow и в комментариях к compose это должно быть явно зафиксировано.

---

### 6. Self-hosted runner и путь к проекту

**Суть:** Workflow запускается на `runs-on: self-hosted`. Код копируется на сервер в `~/ims`. Все команды `docker compose` выполняются по SSH на целевом хосте в `~/ims`. Имя проекта и тома определяются уже там, так что сам по себе runner не меняет том. Важно только, чтобы на сервере всегда работали из одного и того же каталога (например, именно `~/ims`) и не вызывали compose из другой директории с тем же compose-файлом без явного имени тома.

С явным именем тома `ims_ims-db-data` это уже учтено.

---

## Что уже сделано в репозитории

1. **Фиксированное имя тома** в `docker-compose.yaml`: `ims-db-data` → `name: ims_ims-db-data`.
2. **Комментарии** в compose и в workflow: `docker compose down` без `-v` тома не удаляет; на проде не использовать `down -v`.
3. **Рекомендация по деплою:** не вызывать `docker compose down` в pipeline — только `docker compose up -d --build`, чтобы не пересоздавать контейнер Postgres и не рисковать отвязкой тома.

---

## Чек-лист диагностики на сервере

Выполнить на прод-сервере (например, по SSH):

```bash
# 1. Том и его использование
docker volume ls | grep ims
docker inspect ims-postgres --format '{{range .Mounts}}{{.Name}} -> {{.Destination}}{{end}}'

# 2. Содержимое тома (путь к данным)
sudo ls -la /var/lib/docker/volumes/ims_ims-db-data/_data/
sudo ls -la /var/lib/docker/volumes/ims_ims-db-data/_data/data/ 2>/dev/null || true

# 3. К какому Postgres подключается бэкенд
docker exec ims-backend env | grep POSTGRES

# 4. Есть ли данные в БД (из контейнера postgres)
docker exec ims-postgres psql -U $POSTGRES_USER -d ims -c "SELECT COUNT(*) FROM migrations;" 2>/dev/null || true
# (подставить пользователя из .env: BACKEND_POSTGRES_USER)

# 5. Откуда запускается compose и какой project name
cd ~/ims
docker compose config --volumes 2>/dev/null | head -20
```

По результатам можно понять: один ли том используется, не пустой ли он, к тому ли Postgres подключается бэкенд и не переинициализируется ли кластер из-за пути.

---

## Рекомендуемый деплой (без down)

В workflow оставить только поднятие/обновление сервисов:

- Не выполнять `docker compose down` и не делать `docker container prune` / `docker image prune` перед `up`.
- Выполнять только: подготовка `.env`, сертификаты, сборка фронта, затем `docker compose up -d --build`.

Так контейнер Postgres не пересоздаётся при каждом деплое, том остаётся подключённым, данные сохраняются. При необходимости полного перезапуска стека на проде использовать `docker compose down` **без `-v`**, затем `docker compose up -d --build`.
